## Central authorization design
WeekCal now has a two-stage sign-in flow:

1. Identity stage requests only `openid email`.
2. WeekCal submits the Google ID token to the authorization Worker.
3. The Worker validates the token audience against WeekCal's Google Client ID and checks KV.
4. If the account is not authorized, Calendar scopes are never requested.
5. If authorized, WeekCal performs the Calendar OAuth grant using the same Google account.
6. The final identity is checked again to prevent account switching between stages.
7. Connected sessions are revalidated against the central allowlist through `/api/check-access` with a short local cache.

## Authorized-user administration
- Three initial administrator accounts are bootstrapped by SHA-256 hashes only; the public repository does not expose their email addresses.
- Administrators can manage the allowlist from WeekCal Settings → Google Calendar → Usuarios autorizados.
- Add and remove operations are authenticated with the connected Google access token.
- The current administrator cannot remove their own account from the in-app panel.
- Removing a user causes subsequent central authorization checks to fail for that account.

## 0.5.7 OAuth redesign after repeated invalid_request — 2026-09-22
- User confirmed 0.5.6 still returned `invalid_request` on a clean second PC.
- Google’s current installed/desktop OAuth documentation explicitly says incremental authorization is not supported for installed apps.
- The earlier WeekCal design still performed two separate grants (identity first, Calendar second), even after removing `include_granted_scopes`; that remained an incremental authorization pattern.
- WeekCal 0.5.7 now performs a single Google OAuth grant containing identity + Calendar scopes, then checks the central WeekCal allowlist before persisting the tokens.
- The callback now uses the documented root loopback form only: `http://127.0.0.1:<port>`.
- PKCE is now used for every grant.
- The token exchange is performed explicitly against `https://oauth2.googleapis.com/token` with `code`, `client_id`, `redirect_uri`, `grant_type=authorization_code`, `code_verifier`, and the packaged desktop `client_secret` when present.
- Token-exchange errors now expose Google’s `error_description` instead of only the generic `invalid_request`, making any remaining failure diagnosable.
